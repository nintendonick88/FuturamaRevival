# Unresolved Technical Questions and Small Experiments

## Completed first experiments (2026-08-27)

The original three proposed experiments have now been performed, with one necessary change: the production native build ignored the Java `Localhost` preference, so a separately rebuilt preservation client was used after explicit maintainer authorization.

- **Visible controlled-software proof achieved:** a project-controlled HTTP 503 made the game display its own **Connect Error** after it contacted `POST /tapservice/api/`.
- **Exact first request captured:** `RPC: getSalt,getOrCreatePlayerId`, form fields `request` and `chksum`, and the two batched JSON calls are preserved in the experiment log.
- **WOTServer fixture tested:** its JSON was rejected both plainly and with gzip plus its hardcoded `X-TC-Digest`.

Full results and evidence paths are in `docs/EXPERIMENT_LOG.md`.

## P0 — Questions that block a trustworthy bootstrap

1. **Which exact salt/player field values satisfy the two object results inside array-valued `response`?** Native type checks and the rejected named-object test support the array container, but WOTServer's synthetic values still fail.
2. **Does any later path validate `signed_salt`, or is it only forwarded?** The initial callback only stores it. Its production construction and any server-side meaning remain unknown, but an unavailable client-side signing secret is no longer the leading hypothesis.
3. **What configuration/file response contains `server_md5`?** Native tracing separates it from initial bootstrap. Its relation to downloadable content checksums still needs to be mapped; no evidence currently connects it to `X-TC-Digest`.
4. **What does the changing 32-hex-character `chksum` cover?** We need to correlate it with exact request bytes, timestamps, device ID, and any embedded secret before deciding whether the local server must verify or merely ignore it.
5. **What minimum valid response causes the next request, and what is that next request?** This is the immediate experimental target.
6. **Does the client require a particular `player_id`, `human_id`, `community_id`, environment, or response order at bootstrap?**
7. **What is the exact role and host of `process_queue.php`?** Query-field names are known; body and response schemas are not.
8. **Is `/get_server.php` genuine?** It currently has no supporting client evidence.
9. **Are the concurrent Invenio and `tc-bic.appspot.com` calls optional telemetry, or can either block bootstrap after the salt gate?**
10. **Which resources/configuration calls follow player bootstrap, and which must be locally served before a new town can render?**

## P1 — Questions needed immediately after bootstrap

2. Which required downloadable files are absent from the base APK, and do any survive in device/emulator caches?
3. Are protobuf messages used for HTTP transport, local persistence, both, or neither?
4. What are the actual `Player`, `Entity`, `FloorPlan`, `Wallet`, `GoalProgress`, `RandomGenerator`, and `FU` protobuf descriptors?
5. How does client version `1.6.6` relate to `assets/version.txt` value `1.5.0.17` and build revision `103d7d7+`?

7. Does startup contact Firebase, analytics, ads, help, or push services synchronously, or can all third-party failures be ignored?
8. Which server messages are handled by `FUPlayer::setServerMessageHandlers`, and what channel delivers them?
9. Is server time required before local timers and saves initialize?
10. Can an empty/new player be generated by the client, or must the backend return a complete initial `FloorPlan`/town?

## P2 — Preservation and comparative questions

1. What is the exact relationship between Team TSTO's hosted Project Springfield service and BodNJenie's public TSTO private-server repository? The matching developer name and feature set are strong evidence of a relationship, but the production code/version has not been confirmed.
2. Can a matching late-version *Family Guy: The Quest for Stuff* APK provide homologous action names, response envelopes, or protobuf descriptors?
3. Are there WOTServer forks, issues, private notes, packet captures, or later commits outside the inspected public branch?
4. Were the WOTServer `X-TC-Digest` value and nginx header set copied from a real response, derived experimentally, or guessed?
5. Do former players have app-private caches, external-storage download folders, HTTP Toolkit exports, PCAPs, or screenshots from before shutdown?
6. Can historical DNS records or web archives identify exact CDN object paths without contacting or modifying the client?
7. Which static client assets were released content versus unused/debug/Family-Guy carryover?
8. Can we obtain a hash-verified original TSTO **4.70.5** APK? The public repository's committed original is 4.69.5. The present comparison proves surgical native DLC patching, manifest endpoint/package changes, and re-signing, but Apktool resource churn plus the version mismatch prevents an exhaustive logical patch list.
9. Does `game.pjtsto.com` implement the native client's retained `/games/bg_gameserver_plugin/*` contract directly, or does the patched client contain additional routing/adaptation code?
10. Which Project Springfield patcher/backend revision produced the hosted V08 client? Its fixed-width zero-padded `:443` native URL does not match the committed public patcher's `./` padding algorithm.
11. Why does the public server route `/games/{id}/devices` while its own captures show `/rest/v1/games/48302/devices`? Is a prefix stripped elsewhere, is the handler stale, or does the patched client receive a different route from direction data?
12. Which duplicate `akamai.url` entry in the committed direction response does the TSTO client honor, and are the unimplemented port-9000 RTM and `/loader/mobile/.../` destinations ever required?
13. After the attached iPad is unlocked and trusted, can iMazing identify the Project Springfield bundle and preserve its application data? A standard backup/app-data export is not the same as a decrypted reusable IPA; the public `Springfield-V08.ipa` should be preserved and hashed independently first.

## Next three very small experiments

Scores use 5 as highest. For difficulty, 1 is easiest and 5 is hardest. The third experiment is explicitly limited to a disposable preservation build; the original APK remains untouched.

| Overall rank | Experiment | Likelihood | Visible payoff | Difficulty | Learning value |
|---:|---|---:|---:|---:|---:|
| 1 | Test fresh timestamp and stricter trace-supported identity values in the two-object array | 3/5 | 5/5 | 1/5 | 4/5 |
| 2 | Trace the post-parse callback and request-builder preconditions | 4/5 | 2/5 | 2/5 | 5/5 |
| 3 | Add narrowly scoped native diagnostics to a disposable build if static tracing remains ambiguous | 3/5 | 3/5 | 3/5 | 4/5 |

### 1. Test fresh trace-supported values

Keep the two-object response array and vary only the timestamp/signature appearance and identity values supported by native field readers. Keep all transport variables constant.

Success means a new request or a visible loading-state change. Failure narrows the problem to later validation or an unobserved required field.

### 2. Trace the post-parse path

Trace the callback receiving the second result and the first later request-builder preconditions. Identify whether player IDs, environment mapping, salt use, or another bootstrap flag leads to `ENGINE_CONNECT_ERROR`.

Success means an exact, code-backed reason that the parsed values do not advance to the next request.

### 3. Add narrow native diagnostics if necessary

If release logging cannot distinguish the remaining branches, patch a disposable build so only the bootstrap parser's distinct failure branches emit distinguishable diagnostics. Do not bypass parsing or force a successful result.

Success means identifying the exact rejecting branch from runtime evidence without weakening the protocol gate.

## Guardrails for the next pass

- Keep the original APK and WOTServer checkout unchanged.
- Hash and retain every derived APK.
- Record the exact native bytes or smali changed and why.
- Do not invent a player/town schema before the client reveals the next request.
- Do not select a long-term server framework until the initial request sequence is known.
